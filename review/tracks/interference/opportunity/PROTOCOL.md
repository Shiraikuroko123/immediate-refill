# How often can delaying the third request help on archived lengths?

This retrospective workload audit follows the constructed three-request device experiment. The 200 GSM8K questions and the calibration values have already been used elsewhere in the project. The following rules are fixed before calculating this comparison. Record a local UTC timestamp and the SHA-256 of the protocol, analysis program, original shard manifest and sealed device prediction. Require those hashes at analysis time.

Use all eight existing shards of `reasoning-cues/rollouts-qwen4b` at revision `b8c33b85a1a6cdfb23b06a5f9d696f52950780e4`, selected previously in `../holdout/freeze.json`. Within every question use published `rollout_index` 0, 1 and 2 from the first batch, in that order. Verify the source Git blob IDs and the presence of all 16 distinct indices. Record natural generated token lengths and the `hit_token_cap` flag. Keep capped requests at their observed lengths. Report the selected request range, cap count and affected questions. No observations are excluded.

Both fixed policies complete all three requests with the same recorded lengths. Immediate starts all three. Staged starts the first two and starts the third as soon as either finishes, processing tied completions together. The observable completion event suffices to execute both policies. Price the duration of each active-width interval with the sealed median Qwen2.5-1.5B-Instruct A800 step prices from `../prospective-device/session01/prediction.json` for widths 1, 2 and 3. Apply the same prices to every token. No prefill, queueing, sampling changes, votes, or early stopping are modeled. Confirm the event replay against a closed-form occupancy expression per question.

Report the mean and median per-question percent saving from staging, pooled saving, total modeled times and strict counts of positive, negative and equal signs. Also count savings of at least 1% and 2%, with the immediate time as denominator. For the two-action oracle, report the mean and pooled saving from choosing the faster action with complete length knowledge. This is the maximum saving that a selector restricted to those two actions can attain on these questions at the specified fixed clock. A descriptive percentile interval resamples 200 question records with replacement 10,000 times using Python `random.Random(20261120)` and the empirical 2.5% and 97.5% quantiles, linearly interpolated. Report intervals for mean staging and oracle saving. This conditional interval omits clock and publisher uncertainty.

Every timing in this replay is modeled. The archived model is Qwen3-4B-Base. Transport of its lengths to the other model's clock assumes equal service per generated token at each width. The selected three-request subset and published evaluation prompts define the population described here. Occurrence under live user arrivals is unmeasured.
