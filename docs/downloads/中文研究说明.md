# 并行投票时，出现空槽就应立即补发吗？

一道题可以同时生成多条回答，最终按票数决定答案。服务既要尽快得到结果，也要守住每道题允许启动的请求数。多开一条请求可能让它早点完成，也可能拖慢已经在生成的回答。论文研究的是在给定启动顺序、投票规则与解码成本的条件下，什么时候值得等。[英文论文](immediate-refill-paper.pdf) · [中文全文](immediate-refill-zh.pdf)

**为什么有时该等。** 假设同时运行 1、2、3 条路径时，每推进一个解码步分别花 10、11、13 单位时间。有三条必须完成的路径，工作量是 2、1、1。全开要先以宽度 3 运行一步，再以宽度 1 运行一步，共耗时 23。先运行前两条，等短路径完成后补发第三条，就能连续两步维持宽度 2，只耗时 22。这两个调度完成了相同的工作。

**定理解释了何时可以放心补发。** 在不允许比串行投票多启动路径的模型里，所有合法调度对同一个输入都必须完成同一段前缀。贪心把工作更集中地放在较早的虚拟解码时间里。若在所有可达并发宽度上，单步成本随宽度增加的边际增量不递增，即成本曲线离散凹，立即补发对每个面板都最优。若违反这个条件，可以构造延后更快的例子。论文还给出固定成本与槽数、允许面板规模及配额变化时的精确最坏倍率。

**设备上验证了什么。** 在一张 A800 上，先测出各个宽度的单步成本，再预测长度为 256、128、128 的三请求面板。预测延后第三条可省 3.13%，实测 12 个配对区组的中位节时为 2.46%，各区组方向一致。在 200 道归档 GSM8K 题上，前两条同时启动，第三条可立即启动，或等前两条中任意一条先结束。即使预知三条的长度、逐题选更好的动作，平均也只省 0.364% 模拟时间。允许为第三条任意选择启动时刻，这个数字变为 0.764%。

**另一种收益来自更早读取已返回的选票。** 针对同一批 200 道题，用已返回的票决定是否准入下一条路径，相对只处理连续前缀的做法，平均每题减少 8.71% 模拟时间，中位数为 0.14%。把所有题的耗时相加后，节省为 18.72%，其中两道长输出题贡献了约 67% 的净节时。如果基线已经保留前缀内的位置与票值，还统计前缀外每种答案的票数，完整索引只再省 0.30%。另一次 16 题固定工作量的 A800 实测均值为 0.55%，95% 区间跨零。

**怎样复现。** 下载并解压证据包，在解压目录打开终端，使用 Python 3.10 虚拟环境运行下面两条命令。程序在 CPU 上重建保存的设备实验与归档结果，详细结果写入 `results.json`。[证据包](immediate-refill-supplement.zip) · [英文 LaTeX 和绘图源码](immediate-refill-source.zip)

```sh
python -m pip install -r requirements.txt
python -B reproduce.py --out results.json
```
